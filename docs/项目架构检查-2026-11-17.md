### 当前武器边界

- WeaponCatalog：固定类别规则（属性、命中范围）、合法外观及剑染色选项。
- WeaponGeometry：旧默认形状的固定快照，仅供 fallback、箭矢、弓弦和特效使用。
  剑 214 / 弓 192 个格子；迁移前后 cells、stats、hit、bounds 逐项比较一致。
  这里的 region 是模型区域标识，不是可选配件槽位。
- WeaponBuilder / WeaponRig：构建与挂载表现，不再计算配件加成；染色不重建体积或特效池。
- WeaponLoadout：校验、应用完整草稿、选择武器、保存。第二项外观失败或切换拒绝时，
  直接重绑保留的旧材质；回滚无需再次 Clone。保存失败会保留当前装备并明确提示。
- WeaponStore：schema v2，沿用 weapons-v1.json 文件名；载入旧 v1 时保留有效配色和当前武器，
  丢弃 parts。荆棘花弓固定原配色，剑保留三通道染色。
- ForgePanel：只展示完整剑/弓、剑染色、撤销/恢复原色和装备。
  已移除配件页、推荐配装、临时模型比较按钮、属性增减比较及相关死分支。
- 翼剑与荆棘花弓继续使用已认可模型；未改荆棘花弓的 shader、背挂朝向或模型形状。

## 清理前审查

范围：当前 scripts/ 的 125 个 Lua 文件（约 4 万行），重点追踪遗迹入口、场景装配、
战斗/武器/锻造、输入与生命周期，并参考现有离线测试。引擎库和示例不计入用户代码。
这是静态审查加定向离线复现，不是完整 Web 运行验收；没有远端构建、提交或推送。

结论：模块目录已经有了，也未在静态可解析的 require 图里发现环。主要问题是
跨模块职责和状态所有权不清晰、旧玩法数据仍驱动新外观，以及失败路径缺少统一提交/撤销。
不建议按文件行数把函数机械搬走，也不需要推倒现有玩法。

## P1 · 武器外观、玩法参数和旧配件数据还绑在一起

证据：

- scripts/combat/WeaponBuilder.lua:100 的 Assemble 同时拼装体素、累加配件属性、推导命中几何。
- scripts/combat/WeaponRig.lua:831 的 GetHit 和 :839 的 GetStats 都取旧 mesh.blueprint。
- scripts/combat/WeaponRig.lua:1255 的 AttachWing 用旧刀刃长度缩放新剑，再把旧模型缩小隐藏。
- scripts/combat/WeaponRig.lua:1293 的 AttachThorn 也依据旧弓尺寸创建外观，旧模型和池仍保留。
- scripts/ui/ForgePanel.lua:128 起仍展示配件导致的属性差异。

已用真实 Parts.Preset + Builder.Compile 离线计算：

| 武器 | 预设 | attack | 旧剑命中长度 m | 弓 range | draw 参数 |
|---|---|---:|---:|---:|---:|
| 剑 | balanced | 10 | 0.825 | — | — |
| 剑 | fast | 8 | 0.945 | — | — |
| 剑 | armor | 15.5 | 0.825 | — | — |
| 弓 | balanced | 8 | — | 64 | 1 |
| 弓 | fast | 6.5 | — | 49.778 | 0.786 |
| 弓 | armor | 10 | — | 75.236 | 1.335 |

这与已确认的“同类武器只换外观，不靠配件改攻击范围/攻击力”尚未对齐。
换模型已完成，不代表武器数据层已完成迁移。

建议：把同类武器的玩法定义（属性、命中范围、攻击时序）与外观定义（模型、挂点、配色）
分开；Rig 负责挂载和表现，不再通过隐藏的旧网格取得玩法参数。旧体素路径可以保留
为明确的兼容外观。需要同时处理旧存档迁移和锻造控件含义，不能只删除 stats 字段。

## P1 · 锻造应用不是一个完整操作，失败后可能部分生效

证据：scripts/ui/ForgePanel.lua:978 的 Close 逐件调用 rig:Apply，随后才检查
onEquip / CombatState.SetWeapon，最后 Store.Save。scripts/combat/WeaponRig.lua:843
的 Apply 自身又会保存整个 config。UI、Rig、Store 三层共同承担提交职责。

已在 tests/combat/weapon_forge.lua 的现有 UI 测试环境里做内存插入探针：
修改剑配件 → 选弓 → 让切换失败。结果为 equip rejected=true、already applied=1、
panel open=true。复现脚本未改写正式测试文件；结果证明关闭失败前已发生应用。
实际 Rig.Apply 还会提前写存档；测试探针只复现应用顺序，不冒称验证了真实 Web 存档。

建议：独立的装备应用入口负责先准备全部资源和校验切换条件，再一次性发布新配置、
最后保存。UI 只交付草稿与显示结果，Rig.Apply 不直接保存。失败保留旧装备和草稿，
资源准备中途失败清理临时对象；避免“先改一个，再发现另一个不能改”。

## P1 · RuinsScene 负责过多细节，更新顺序成为隐式约定

scripts/ruins/RuinsScene.lua 当前 2004 行，静态引用 48 个项目模块。它同时管理：

- :579 StartCombat：战斗、箭发射与命中、敌人、跑步、武器轮盘、反馈装配。
- :1072 至 :1237：传送、木桩、动画预览和自动测试入口。
- :1320 SceneUpdate：输入采样、战斗动作和角色物理意图。
- :1586 Update：骑龙、敌人、法术、动画叠加、武器、谜题、天气和 HUD。
- :1928 PostUpdate：最终相机、瞄准表现、法阵与轮盘定位。
- :1949 Stop：手工逐个关闭子系统。

当前帧序有合理原因（物理意图先提交、最终骨骼后采样、最终相机后更新 HUD），
但依赖散在闭包和直接字段赋值中。修改一处相机或动作，很容易影响轮盘、骑乘或法术。

建议保持 SceneUpdate / Update / PostUpdate 顺序，先抽出独立 DebugSession，
再抽 CombatSession（创建、更新、关闭归一个实例）。RuinsScene 保留装配与明确的阶段调用。
不要把同一组可变 local 放进万能 ctx 后跨文件任意改写，那只是把耦合藏起来。

## P1 · 场景重建缺少成对的状态初始化/释放

证据：scripts/ruins/RuinsPuzzles.lua:34-46 在模块加载时建立 objects/list/steps/events，
Add 和 On 只追加；:650 Build 没有清空它们，却会重新创建对象并订阅体素事件。
scripts/ruins/RuinsScene.lua:837 每次 Start 都调用 Build 与 On(OnPuzzle)，
而 :1949 Stop 没有对应 Puzzles.Stop。

由代码可确认：同一 Lua VM 内再次 Start，会沿用旧进度、追加旧对象列表和回调。
正常网页刷新若销毁整个 VM，不会走这个条件；不能据此声称当前每次打开网页都泄漏。
原生资源持有和事件释放的实际后果仍需 Web 同 VM 重建验证。

建议定义场景实例生命周期：Puzzles.New/Dispose 或清晰的 Build/Stop；
解绑自己订阅的事件、清空自己的引用与回调，把“开始新局”和“保留进度重建”明确分开。
加同 VM 的 Start → Stop → Start 回归，检查对象数、回调次数和进度是否符合预期。

## P2 · 输入权限和界面显示规则分散

证据：RuinsScene.lua:1325 与 :1627 分别拼接移动/战斗 allowed 条件；
另有 combatInputBlocked、voidInputBlocked、pointer 状态、骑乘状态。
SettingsMenu.IsBlocked、WeaponWheel.IsBlocked 和 ForgePanel.IsOpen 分别维护释放锁。
TouchControls.lua:15、CombatHUD.lua:9、PerformanceHUD.lua:10 还读取 package.loaded
或 FORGE_HUD_HIDDEN 获取锻造隐藏状态，同时又存在显式注入 getter 的主路径。

这些保护本身有必要，风险在于新增一个界面就要同步多个判断；静态无循环依赖
也不等于没有这些运行时旁路依赖。当前审查未复现新的点击穿透 bug。

建议由一个输入权限模块产出当帧 canMove/canLook/canAttack/canCast；
释放锁仍保留，但把阻塞原因和解除时机集中管理。HUD 可见性经一个显式接口传递。
